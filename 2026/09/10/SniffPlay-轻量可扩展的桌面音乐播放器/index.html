SniffPlay：一个轻量、可扩展的桌面音乐播放器

项目地址：https://github.com/gaoshoulailo/SniffPlay
当前版本：v0.1.6
适用系统：Windows 10 / 11

SniffPlay，一个使用 Python、PySide6 和 QML 开发的轻量桌面音乐播放器。

它既可以通过可扩展的音乐源搜索公开音视频资源，也可以播放本地音频，并在本机管理收藏、歌单和播放历史。不过，这个项目真正想解决的并不只是“把音乐播放出来”，而是如何把界面、音乐来源、播放内核和本地数据拆分开，让每一部分都可以独立替换和扩展。

一、为什么要做 SniffPlay

音乐播放器看起来并不复杂：搜索歌曲、拿到地址、交给播放器播放。但真正开始写之后，会遇到几个比较实际的问题：

  1. 网络播放地址往往具有时效性，不能直接保存下来长期使用
  2. 播放状态、队列、收藏和歌单很容易全部堆进界面代码
  3. 桌面应用还需要考虑本地数据、日志、打包和运行环境

SniffPlay 的思路是先把这些边界划清楚，再实现具体功能。

项目的重点不只是“目前支持什么”，而是新增一个音乐源、更换播放器实现或扩充数据功能时，不需要重写整个应用。

二、目前已经实现的功能

当前版本已经覆盖了一个桌面音乐播放器的主要使用流程。

1. 在线搜索与播放

SniffPlay 使用统一的音乐源接口接入在线公开资源。不同来源可以拥有完全不同的请求、认证和数据解析方式，但返回给播放器的都是统一歌曲模型。

播放前，程序会通过歌曲所属的音乐源解析实际音频流，并将播放地址和所需请求头交给播放内核。各音乐源还可以根据自身特点处理签名、清晰度选择、超时重试和地址刷新。

当前版本内置了一个基于 Bilibili 公开资源的实现，它只是 Provider 架构的一个实例，并不是播放器与生俱来的限制。

网络播放地址只在真正播放前解析，不会写入数据库。这样可以避免收藏或歌单中保存一个很快就会过期的链接。

2. 本地音频播放

除了在线资源，也可以直接打开本地音频。目前支持 MP3、FLAC、WAV、M4A、AAC、OGG、Opus 等常见格式。

本地歌曲与在线歌曲会进入同一套播放队列，因此播放、暂停、进度跳转、音量控制、上一首、下一首和自动续播等操作不需要区分资源来源。

3. 播放队列与循环模式

播放器支持：

  • 顺序播放
  • 列表循环
  • 单曲循环
  • 随机播放
  • 从搜索、收藏、歌单或历史中的指定歌曲开始播放
  • 调整当前队列、下一首播放和移除队列歌曲

这部分逻辑集中在控制器中，QML 界面只负责展示状态和发送操作，不直接维护真正的播放规则。

4. 收藏、歌单和播放历史

SniffPlay 使用 SQLite 保存本地数据，目前可以：

  • 收藏或取消收藏歌曲
  • 创建、重命名和删除歌单
  • 向歌单添加或移除歌曲
  • 调整歌曲在歌单中的顺序
  • 播放整个歌单或从指定歌曲开始播放
  • 从收藏和历史中重新播放或加入歌单

播放历史并不是点击歌曲后立即写入。只有歌曲达到有效播放阈值才会记录，从而避免快速试听产生大量无意义数据。

5. 桌面界面与本地配置

界面使用 PySide6 + QML 构建，采用无边框深色设计。搜索、正在播放、收藏、歌单、历史和设置分别拆成独立页面，底部播放栏则作为公共组件复用。

应用还支持自定义背景颜色和背景图片。数据库、日志和封面缓存统一保存在应用的 data 目录中，也可以通过 SNIFFPLAY_DATA_DIR 指定其他位置。

三、整体架构

SniffPlay 没有让 QML 直接访问网络、数据库或 libmpv，而是按职责拆成了几个层次：

各部分的职责如下：

  1. QML 界面层 —— 展示状态并接收用户操作
  2. AppController 控制器层 —— 连接 QML 与 Python，协调搜索、播放和本地数据
  3. SearchService 服务层 —— 聚合多个音乐来源，统一搜索和播放地址解析
  4. Provider 音乐源层 —— 隔离不同站点的请求、签名、解析和错误处理
  5. Player 播放层 —— 屏蔽具体播放内核，对外暴露统一播放接口
  6. Repository 数据层 —— 管理歌曲、收藏、歌单、历史和设置

分层的意义不是让目录看起来整齐，而是限制依赖方向。例如任何音乐源 Provider 都不需要知道界面长什么样，也不能直接操作数据库。

四、可扩展性是怎么实现的

1. 音乐来源可以独立接入

所有音乐来源都实现同一个 MusicProvider 接口：

一个新的 Provider 只需要完成两件事：

  1. 把来源站点的搜索结果转换成标准 Track
  2. 在播放前把歌曲转换成标准 StreamInfo

实现后将它注册到 ProviderRegistry，SearchService 就可以并发搜索所有已启用来源。某一个来源请求失败时，只会忽略该来源的结果，不会让整个搜索一起失败。

Provider 只关心自己的数据源，不直接操作 QML、播放器和数据库。这是 SniffPlay 最重要的扩展边界。

2. 本地与在线歌曲使用同一模型

无论歌曲来自哪个在线平台或本地文件，上层拿到的都是统一 Track 对象。

provider_id 和 provider_track_id 用于标识歌曲来自哪里；playback_uri 存在时可以直接播放，否则再交给对应 Provider 解析临时地址。

这样一来，收藏、歌单、历史和播放队列都不需要为每个音乐来源单独写一套逻辑。

3. 播放内核可以替换

当前版本使用 libmpv 解码和播放音频，但控制器依赖的是抽象 Player 接口，而不是 libmpv 的具体方法。

这个接口统一定义了：

  • 播放歌曲
  • 暂停与继续
  • 进度跳转
  • 音量设置
  • 播放状态快照
  • 资源释放

以后如果要接入其他播放后端，只需要实现相同接口。即使系统中缺少 libmpv，应用也会切换到 UnavailablePlayer 安全降级，界面、搜索、收藏和歌单功能仍然可以正常启动。

4. 数据访问与业务逻辑分离

收藏、歌单、历史和设置分别由 Repository 管理，上层不直接编写 SQLAlchemy 查询。

这种设计让数据库字段调整、查询优化和数据迁移集中在数据层，也让控制器测试不必绑定真实数据库实现。未来新增“最近常听”“播放次数统计”或“歌单导入导出”时，也有清晰的落点。

5. 界面组件可以继续复用

QML 页面、通用按钮、导航按钮、右键菜单和底部播放栏已经拆分。颜色、字体和圆角等视觉参数集中在 Theme 中管理。

当前版本虽然还是固定深色主题，但结构已经为浅色主题、更多配色和运行时主题切换留下了空间。

五、通用的数据源处理机制

不同音乐平台的接口形式各不相同：有的需要请求签名，有的需要临时令牌，有的返回多种音质，还有的播放地址会很快过期。SniffPlay 将这些差异留在各自的 Provider 内部，上层业务只处理统一结果。

1. 搜索结果标准化

Provider 负责把来源平台的字段转换成标准 Track，包括歌曲标识、标题、作者、专辑、时长和封面等信息。

这样一来，搜索结果进入控制器后就不再带有平台特有的数据结构。界面、收藏、歌单和历史记录都可以用同一套代码处理。

2. 播放地址即时解析

在线音频地址可能存在有效期，因此数据库只保存歌曲身份和基础信息，真正播放时再调用对应 Provider 的 resolve_stream()。

解析结果统一为 StreamInfo，其中既可以包含播放 URL，也可以附带远程资源需要的 HTTP 请求头。播放层不必了解地址是如何获取的。

3. 来源级错误隔离

SearchService 会并发调用所有已注册的 Provider。某个来源暂时不可用时，其他来源仍然可以正常返回结果，避免单个平台故障拖垮整个搜索流程。

每个 Provider 也可以独立实现超时、重试、令牌刷新、限流处理和错误转换，不需要把平台特有的容错逻辑塞进控制器。

4. 封面与临时资源缓存

搜索结果的远程封面会并发下载到本地缓存。下载过程限制了并发数、单张图片大小和整批等待时间，单张封面失败不会影响搜索结果展示。

通过本地缓存，重复打开收藏或歌单时不必每次重新请求远程图片，也能减少界面滚动时的网络波动。

对新的音乐来源来说，需要变化的主要是 Provider；播放器界面、播放队列和本地管理功能可以直接复用。

六、性能、稳定性与工程化

桌面播放器需要长时间运行，因此稳定性和资源占用比短时间跑通 Demo 更重要。

SniffPlay 使用 libmpv 完成实际音频解码，Python 不需要持续处理音频数据。控制器每 250ms 获取一次播放状态，在进度显示流畅度和轮询开销之间做了平衡。

目前开发机的静音播放基线数据如下，仅供参考：

状态 总 CPU 工作集
应用空闲 约 0.02% 约 123 MB
完整应用播放 约 0.20% 约 129 MB

项目还包含以下工程化能力：

  • pytest 单元测试和异步测试
  • QML 静态检查
  • Python 编译检查
  • GitHub Actions Windows 自动测试
  • PyInstaller one-folder 便携打包
  • 打包后的启动烟雾测试
  • 固定 libmpv 版本并校验 SHA-256
  • 推送版本标签后自动生成草稿 Release
  • 滚动日志，避免日志文件无限增长

能运行只是第一步，能够重复测试、稳定打包和明确追踪第三方组件版本，才更接近一个可以持续维护的桌面项目。

八、当前边界与后续方向

已完成

  • PySide6 + QML 桌面界面
  • 可扩展音乐源的公开资源搜索与在线音频播放
  • 本地常见音频格式播放
  • 播放队列、随机播放和循环模式
  • 收藏、歌单和有效播放历史
  • SQLite 本地持久化
  • 封面缓存、网络重试和错误降级
  • Windows 本地打包与 GitHub 自动构建
  • Provider、Player 和 Repository 扩展边界

当前限制

  • 当前内置在线源的分页与多段媒体支持仍有限
  • 音乐源的图形化启用、停用和配置功能尚待完善
  • 暂不支持账号登录或会员资源
  • 暂无歌词、下载和均衡器
  • 暂无安装包和自动更新
  • 暂未提供运行时主题切换

后续扩展可以围绕新的合规音乐来源、歌词展示、歌单导入导出、播放统计、主题系统和更完整的 Windows 发布体验展开。

接入第三方音乐来源时，仍然需要遵守目标站点的服务条款、版权要求和访问规则，不应绕过登录、付费或其他访问控制。

九、总结

SniffPlay 目前还是一个持续迭代中的项目，但搜索、播放、队列和本地音乐管理已经形成了完整闭环。

它的优势并不在于功能数量堆得多，而在于几个核心模块之间保持了清晰边界：音乐源负责把外部数据转换成统一模型，播放器负责播放，Repository 负责持久化，QML 负责界面，控制器负责协调。

正因为这些边界已经提前划分好，项目以后增加音乐来源、替换播放内核或扩展本地管理功能时，改动都可以控制在对应模块中。

🔨 SniffPlay 仍在持续更新中，项目源码与最新版本请以 GitHub 仓库为准。
